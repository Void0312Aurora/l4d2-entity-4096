# N4：`max_edicts` 的语义边界、`0x11C` 帧布局的归属冲突、虚槽号更正

> 本轮回答 review 提的两个 P0：`sv.max_edicts` 的静态可达性，以及 `0x11C` 帧对象能否按
> 「位图扩 256→512 字节」整体迁移。第一项给出了强静态结论；第二项**没有**通过：证据链内部
> 出现一个冲突，必须先解决它，`0x11C→0x21C` 才可写入 manifest。

## 0 结论

| 项 | 结论 | 等级 |
|---|---|---|
| `max_edicts` 的语义 | **索引的排他上界**（`0 ≤ i < max_edicts`），因此是容量计数，不是「最大索引」 | 已证实 |
| `num_edicts` 能否达到 `max_edicts` | `ED_Alloc` 的成长条件允许；`max-1 → max` 可达 | 已证实（静态） |
| 4096 时 `w_max` | **13**（`N ∈ [0,4096]`） | 强静态，仍待 C5 运行时复核 |
| `0x11C → 0x21C` 迁移 | **冲突已解（§3.4）**：`+0x38` 是**快照**的引用计数，不是帧的字段；帧内 256 B 位图假设自洽，迁移可列入清单（置位点尚未直接观察） | 高置信 |
| 虚槽号 | 更正为：**槽偏移 `+0x80`、索引 32 已确认**；未确认的是虚表身份与目标函数 | 已更正 |

## 1 `max_edicts` 的语义：`EDICT_NUM` 给了排他上界

`FUN_101E0000`：

```c
int FUN_101e0000(int i) {
  if ((i < 0) || (DAT_10645770 <= i))          // 上界是排他的
    FUN_101fc620("EDICT_NUM: bad number %i", i);
  return i * 0x10 + DAT_10645774;              // edicts 数组，步长 0x10
}
```

字符串 `"EDICT_NUM: bad number %i"` 定位函数身份；`DAT_10645770 <= i` 说明
**合法索引集合是 `[0, max_edicts)`**。结合 `ED_Alloc` 的 `param_1 < DAT_1064576c`
（§N3 2.3），三者现在是同一个量纲：

| 全局 | 语义 | 判据 |
|---|---|---|
| `0x1064576C` `num_edicts` | 已分配 edict 数 | `ED_Alloc` 唯一 `INC` |
| `0x10645770` `max_edicts` | 索引上界（= 容量） | `EDICT_NUM` 的 `<=`；`ED_Alloc` 的成长闸门 |
| `0x10645774` `edicts` | 数组基址 | 两处 `i*0x10 + base` |

所以 `max_edicts` 是**计数语义**，`max_edicts = 4096` 时合法索引是 `0..4095`。

## 2 最后一次合法分配可达 ⇒ `N_max = max_edicts` ⇒ `w_max = 13`

`ED_Alloc` 的成长分支：

```c
if (DAT_10645770 <= DAT_1064576c) {          // max <= num：失败
    ... FUN_101fc620("ED_Alloc: no free edicts");
}
DAT_1064576c = DAT_1064576c + 1;             // 否则 ++
```

取 `num = max - 1`：条件 `max <= max-1` 为假 → 走 `++` → `num = max`。**这一步不需要额外前提**，
只要分配请求真的发生。`EDICT_NUM` 只在 `i >= max` 时报警，而 `i = max-1` 仍合法，
所以「填满到 `num = max`」不触发断言。

快照构建侧（N3 §2.2）用 `num_edicts` 作为容量并遍历 `[0, num_edicts)`，没有任何「`num == max`
时改用 `max-1`」的分支。因此：

$$
N_{\max} = \text{max\_edicts} = 4096 \;\Longrightarrow\; w_{\max}=\lceil\log_2(4096+1)\rceil = 13
$$

review 给的这条控制流证明成立；我把它记为 **C1″（强静态，13 位必要性）**。
仍未闭合的只剩：

- **C5（原版满容量行为）**：`max_edicts = 2048`、`num_edicts = 2048` 时，11 位字段把 2048 编成 0。
  这是**原版既有边界**，需要在运行时把 `num_edicts` 顶到 2048 观察线上行为，不应算作扩容引入；
- **C8（写入点）**：`0x10645770` 的赋值来源仍未定位。本轮新增两条否证：

```
C7 ?? 70 07 00 00 00 08 00 00   (mov dword [reg+0x770], 0x800)   -> 0 命中
89 ?? 74 07 00 00               (mov [reg+0x774], reg)            -> 0 命中
```

  说明初始化**不是**「常量 0x800 直接落到 `+0x770`」，而是来自寄存器/结构初始化/`sv` 整体拷贝。
  下一步应从 `SV_SpawnServer` 的 `0x800` 常量反向找消费者，而不是继续扫绝对地址。

## 3 `0x11C` 帧布局：字段已定，位图归属未定（迁移暂缓）

### 3.1 构造器写点（`FUN_10093E20`，全部为实参/立即数写入）

| 偏移 | 内容 | 写点（伪代码） |
|---|---|---|
| `+0x00` | vptr `PTR_FUN_1036ac28` | `*in_ECX = ...` |
| `+0x04` | 0 | `in_ECX[1] = 0` |
| `+0x08` | `snapshot->+0x04`（tick） | `in_ECX[2] = *(param_1+4)` |
| `+0x0C .. +0x10B` | **`memset(0, 0x100)`** | `_memset(in_ECX+3, 0, 0x100)` |
| `+0x10C` | 0 | `in_ECX[0x43] = 0` |
| `+0x110` | 0 | `in_ECX[0x44] = 0` |
| `+0x114` | 0（链表 next） | `in_ECX[0x45] = 0` |
| `+0x118` | 快照指针 | `in_ECX[0x46] = param_1` |

链表语义由 `FUN_10093C80` 独立确认：结点 `+0x08` = tick、`+0x114` = next。

### 3.2 冲突：`+0x38` 的原子自增落在 memset 区间内

构造器在 `memset(+0x0C, 0, 0x100)` 之后、写 `+0x118` 之前调用：

```c
in_ECX[0x46] = 0;          // +0x118
FUN_1011c290();            // ECX = this（同一寄存器，未重装）
if (in_ECX[0x46] != 0) FUN_1011db40();
in_ECX[0x46] = param_1;    // +0x118
```

而 `FUN_1011C290` 是：

```c
int FUN_1011c290(void) {
  int *p = (int *)(in_ECX + 0x38);     // <<< +0x38
  LOCK(); iVar1 = *p; *p = *p + 1; UNLOCK();
  return iVar1;
}
```

`0x38` 落在 `0x0C..0x10B` 内。若该 256 字节真是 inline 位图，这个 `LOCK XADD` 会改到位图；
若 `+0x38` 是引用计数/句柄，则 256 字节不是位图（或不是从 `+0x0C` 起连续占用）。

三种可能，必须择一：

1. **位图假设成立** → `+0x38` 的调用发生在**另一个对象**上（ECX 在调用前被重装，伪代码未显示）；
   需要逐指令核对 `0x10093E2x..0x10093E7x` 的寄存器流。
2. **`+0x0C` 不是位图** → 256 字节是别的定长表（例如按客户端/玩家索引的槽位表），
   则「位图扩到 512 字节 ⇒ 对象 0x21C」的前提不成立，帧布局**保持不变**。
3. **两处都在同一对象** → 现版就是重叠写（可能性最低，但不能先验排除，需运行时观察）。

在这一点解决前，`sizeof(CFrame): 0x11C → 0x21C`、`snapshot: +0x118 → +0x218`、
`next: +0x114 → +0x214` **都不应写入补丁清单**——否则会把一个未证实的偏移迁移，
扩散到 `FUN_10119F50`、`FUN_10093C80`、`FUN_101846C0` 三处读取点。

### 3.3 两个位图必须分账

N2 记过「`+0x10C` 位图」，N3 记了帧内 `memset(+0x0C,0x100)`，`FUN_101196C0` 又在 `+0x3C`
用 2048 位掩码。三者尺寸/偏移不同，**不是同一个对象**：

| 编号 | 位置 | 尺寸 | 已知字段 | 归属 |
|---|---|---|---|---|
| BM-1 | `FUN_10093E20` 帧 `+0x0C` | 256 B（memset 0x100） | 与 `+0x38` 冲突 | **未定**（本轮冲突点） |
| BM-2 | `FUN_101196C0` 接收端 `+0x3C` | 256 B（`+0x3C..+0x13B`） | `+0x13C`/`+0x140` 为两个快照、`+0x14` 为索引 | 报文解析对象 |
| BM-3 | N2 的 `+0x10C` | 待核 | — | 待核 |

review 的「类型隔离」要求成立：**BM-1 与 BM-2 不能共用一条迁移假设**。

## 4 更正：虚槽号可以声称，虚表身份不能

N3 写「不能计算槽位索引」过严。32 位下 `call dword ptr [eax+0x80]` 的槽号是纯算术：

$$
\text{slot} = 0x80 / 4 = \boxed{32}\ \text{（从 0 计数）}
$$

因此正确的记法是：**槽偏移 `+0x80`、索引 32 已确认**；未确认的是
（a）`[edi-8]` 指向哪张虚表，（b）槽 32 的目标函数，（c）是否经过 this 调整 thunk，
（d）该目标是否消费 `UpdatedEntries`。本轮未新增这条链的证据。

## 5 `U_max` 不能随手扩到 4096

N3 的 `U_max ≤ 2048` 来自 `FUN_1004E310` 的 `0x800`/`0x40`。位图扩到 4096 位后，
这组常量会变成 `0x1000`/`0x80`，但**新的上界能否达到 4096** 取决于：

1. `FUN_101196C0` 的索引递增上限（`+0x14` 与 `count_B` 的关系）；
2. 单包 delta 生成端是否允许「全部实体都被更新」；
3. 是否存在分包/分片上限（N2 §9 的三个 2048 边界里可能有交叉约束）。

所以 `m_nMaxEntries` 与 `m_nUpdatedEntries` 的位宽需求**必须分开证**：
前者由 §2 的 `max_edicts` 给出（13），后者仍是 `U_max` 的开问题。

## 3.4 追加：冲突已解决 —— `+0x38` 属于快照，不属于帧

上一节把 `FUN_1011C290` 当成「在帧对象上做原子自增」，据此与 `memset(+0x0C,0,0x100)` 冲突。
逐指令核对 `FUN_10093E20` 的寄存器流后，冲突不成立：

```
0x10093e46: MOV EDI, dword ptr [EBP + 0x8]   ; EDI = param_1 = 快照
0x10093e49: MOV dword ptr [ESI + 0x4], EBX
0x10093e4c: MOV dword ptr [ESI + 0x110], EBX
0x10093e52: MOV dword ptr [ESI + 0x10c], EBX
0x10093e58: MOV EAX, dword ptr [EDI + 0x4]   ; 快照 tick
0x10093e5b: MOV ECX, EDI                     ; <<< ECX = 快照，不是 ESI(this)
0x10093e5d: MOV dword ptr [ESI + 0x8], EAX
0x10093e60: MOV dword ptr [ESI + 0x118], EBX
0x10093e66: CALL 0x1011c290                  ; AddRef(snapshot)->[snapshot+0x38]
0x10093e6b: MOV ECX, dword ptr [ESI + 0x118] ; 旧快照
0x10093e71: CMP ECX, EBX
0x10093e73: JZ 0x10093e7a
0x10093e75: CALL 0x1011db40                  ; Release(旧快照)
0x10093e7a: MOV dword ptr [ESI + 0x118], EDI ; <<< frame+0x118 = 快照
0x10093e81: MOV dword ptr [ESI + 0x114], EBX
0x10093e8c: RET 0x4
```

结论：

1. `FUN_1011C290` 的 `+0x38` 是**快照对象**的引用计数（与 N2 §14.2 的快照布局一致），
   帧对象 `0x0C..0x10B` 的 256 字节区域与它无关；
2. 帧构造器对 `this` 的写入只有 7 处：`+0x00`、`+0x04`、`+0x08`、`memset(+0x0C,0x100)`、
   `+0x10C`、`+0x110`、`+0x114`、`+0x118` —— 尺寸账正好配平：
   `0x0C + 0x100 + 0x10 = 0x11C`；
3. 因此 `0x11C → 0x21C` 的迁移在**结构上成立**，可进入 manifest，但需带两个保留条件：
   - 帧内 `+0x0C` 的 256 字节**尚未观察到置位指令**（只有 ctor 的 memset 与尺寸配平），
     所以「它是 2048 位位图」仍属高置信推断而非直接观测；
   - 迁移牵动 3 个读取点：`FUN_10119F50`（`[frame+0x118]`）、`FUN_10093C80`（`next` 在 `+0x114`）、
     `FUN_101846C0`（`[frame+0x118]` 与条目拷贝），必须同批改。

### 3.5 迁移清单（若 §3.4 的位图用途被后续置位点证实）

| 成员 | 旧 | 新 | 位移 |
|---|---|---|---|
| inline 位图 | `+0x00C` | `+0x00C` | 起点不变，尺寸 256→512 B |
| 位图尾后的 dword | `+0x10C` | `+0x20C` | +0x100 |
| 未命名字段 | `+0x110` | `+0x210` | +0x100 |
| 链表 next | `+0x114` | `+0x214` | +0x100 |
| 快照指针 | `+0x118` | `+0x218` | +0x100 |
| `sizeof` | `0x11C` | `0x21C` | +0x100 |

对应读取点：`0x10119fbf/0x10119fcb`（`param2->0x118`）、`0x10093c80` 的 `+0x114`、
`0x101846c0` 的两处 `+0x118` 与 `+0x30` 循环里的条目指针。
