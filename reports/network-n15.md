# N15：扫描器的位图基址是 `(*[EDI+8])+0x0C`，不是编码器内联的 `+0x3C`

> 本轮只做一件事：把 `FUN_101196C0` 内部那次 `FUN_1004E310` 调用的 `ECX` 定下来。
> 结果比预期更有信息量——它**不是**直接传 `EDI+0x3C`，而是传 `[[EDI+8]]+0x0C`。
> 这既确认了 review 指出的越界写入风险，也打开了一条能判定「两处位图是否同一块」的验证路径。

## 0 结论

| 项 | 结果 |
|---|---|
| `CALL 0x1004E310` 位置 | `0x10119731`，参数为 `index+1` |
| `ECX` 到达定义 | `0x1011972e LEA ECX,[EAX+0xC]`，其中 `EAX = [EDI+8]` |
| 因此位图基址 | `(*[EDI+8]) + 0x0C` |
| 与 `EDI+0x3C` 的关系 | **尚未证明同一**；若构造器写入 `[EDI+8] = EDI+0x30`，则 `+0x0C` 恰好等于 `+0x3C` |
| 越界写入风险 | 成立（条件同上）：`i = 2048` 时 `+0x3C + 0x100 = +0x13C`，即新快照指针 |
| 旧快照数组先读后查计数 | **已证实**（`0x101196e9` 早于 `0x101196f0`） |

## 1 调用点的逐指令证据

```
0x10119715  MOV  EAX,[EDI+0x14]      ; index
0x10119718  PUSH ESI                 ; flags
0x10119719  PUSH EAX                 ; index
0x1011971a  CALL 0x10119370          ; ParseDelta(index, flags)
0x1011971f  MOV  EAX,[EDI+0x8]       ; <<< 指针 P
0x10119722  ADD  ESP,0x8
0x10119725  TEST EAX,EAX
0x10119727  JZ   0x1011973d          ; P == NULL -> 直接置哨兵
0x10119729  MOV  ECX,[EDI+0x14]      ; index
0x1011972c  INC  ECX                 ; index+1
0x1011972d  PUSH ECX                 ; 参数 = index+1
0x1011972e  LEA  ECX,[EAX+0xC]       ; <<< 位图基址 = P + 0x0C
0x10119731  CALL 0x1004e310          ; FindNextSetBit(index+1)
0x10119736  MOV  [EDI+0x14],EAX
0x10119739  TEST EAX,EAX
0x1011973b  JNS  0x10119744
0x1011973d  MOV  dword [EDI+0x14],0x270f   ; 9999 哨兵
```

与 `FUN_1004E310` 的契约（N14）对照：`ECX` 就是位图基址，参数是起始索引。
所以被扫描的位图 = `(*[EDI+8]) + 0x0C`。

## 2 置位与扫描是否同一块位图：待证的自指针假设

置位侧（同一函数）：

```
0x101196fe  MOV  EAX,ECX              ; index
0x10119705  SAR  EAX,0x5
0x1011970a  LEA  EAX,[EDI+EAX*4+0x3c]; <<< 内联位图 EDI+0x3C
0x10119713  OR   dword [EAX],EDX      ; 置位
```

若 `[EDI+8] == EDI+0x30`，则：

$$ (\ast[\mathrm{EDI}+8])+0x0C = \mathrm{EDI}+0x30+0x0C = \mathrm{EDI}+0x3\mathtt{C} $$

两处就自动成为**同一块位图**。这类「结构体在 `+8` 保存指向自身子对象的指针」在 Source 引擎里很常见
（子对象偏移 `+0x30`，而子对象的第一个数组成员在 `+0x0C`）。

验证方法（下一轮，一次即可判定）：

1. 找 `FUN_101196C0` 所属对象的构造器/初始化点，检查是否有 `LEA reg,[reg+0x30]; MOV [reg+8],reg`；
2. 或直接查 `MOV [reg+8], …` 且右侧来自 `+0x30` 的编码；
3. 若成立，则「置位 `+0x3C`」与「扫描 `(*[+8])+0x0C`」是同一块 2048 位位图。

## 3 review 指出的两个边界，逐条核对

### 3.1 越界写入（确认，条件性）

`i = 2048` 时：

$$ \mathrm{EDI}+0x3\mathtt{C} + (2048 \gg 5)\times 4 = \mathrm{EDI}+0x13\mathtt{C} $$

而 `+0x13C` 正是**新快照指针**（`MOV EDX,[EDI+0x13C]`，随后 `[EDX+0xC]` 取计数、`[EDX+0x8]` 取数组）。
也就是说，第 2048 号实体一旦进入置位分支，会 `OR` 到指向快照结构的指针上——**指针损坏**，
比「扫描截断」严重。

顺带：`+0x140`（旧快照指针）在 `i = 2049`..`2079` 时同样会被覆盖。

### 3.2 旧数组先读、后查计数（确认）

```
0x101196e9  CMP dword [EAX+EBX],0x0    ; EBX = [*[EDI+0x140] + 8]（旧快照数组）
0x101196f0  CMP ECX,[EDX+0xC]          ; 之后才检查 i < 新快照计数
```

汇编顺序与伪代码一致：旧快照数组的读取发生在边界检查之前。若两快照容量不同，
这就是独立于位图的第一条越界路径。需要单独确认旧快照数组的容量来源。

### 3.3 扫描器尾端多读一个 dword（确认形态）

`FUN_1004E310` 的循环是「先读 `p[1]`、再判断 `i < 0x40`」。当最后一个 dword 无置位时，
会先读 `bitmap+0x100` 处的 4 字节再退出。原布局里这正是 `+0x13C` 快照指针的低 4 字节——
只读，不写，但属于越界访问。扩容到 512 字节后该地址变成 `+0x23C`（新布局的快照指针），
同样需要保证可读。

## 4 N4-F：delta 编码器对象扩容（独立工作单）

| 成员 | 原偏移 | 目标偏移 |
|---|---|---|
| 2048 位内联位图 | `+0x03C`（0x100 B） | `+0x03C`（0x200 B） |
| 新快照指针 | `+0x13C` | `+0x23C` |
| 旧快照指针 | `+0x140` | `+0x240` |
| 最小 `sizeof` | ≥ `0x144` | ≥ `0x244` |

实际 `sizeof` 必须由构造器/分配点确认（当前只从字段上界推断）。迁移时还要同步：

- `0x10119713` 的 `OR` 目标（`+0x3C` 不变，容量变 512 B）；
- `0x101196d2/0x101196d9` 的 `+0x13C`/`+0x140` 读取；
- `0x1011972e` 的 `LEA ECX,[EAX+0xC]`（若 `[EDI+8]` 是自指针，则无需改；若是外部指针，需另核）。

## 5 术语与归属（保持谨慎）

`FUN_101196C0` 目前只能称为「参与实体 delta 处理的对象」，**不能**断言它是发送端编码器还是接收端解析器：
它的 `this` 通过 `EAX` 传入（`MOV EDI,EAX`），不是标准 `ECX` this-call，说明它更可能是**回调/虚表槽**，
由某个循环以寄存器约定调用。这一点需要在确定调用者后再定性，且会影响 N4-F 的迁移归属。
