## 1 路径 B 否定：`0x10123B20` 不在任何指针表中

对 `20 3B 12 10`（小端 `0x10123B20`）做全镜像搜索，覆盖 `.text`/`.rdata`/`.data`/`.rsrc`/`.reloc`：

```
matches: []      complete: true      bytes: 7,586,372
```

因为该镜像 `ImageBase = 0x10000000` 且 `.data` 中的函数指针在 PE 里就是绝对 VA，
虚表槽位/函数指针表若存在必然命中。**0 命中说明 `SV_SpawnServer` 不是虚函数**，
也不在任何静态分发表里。

推论：

- review 提出的「`mov ecx,0x10645558; mov eax,[ecx]; call [eax+N]`」形态对本函数不成立；
- 因此**不需要**再做虚表/COL/槽位恢复（先前为 `[[edi-8]+0x80]` 准备的那套方法不适用于此）；
- 剩余可达路径：直接 `E8 rel32`，或运行时计算地址（无静态证据，暂不假设）。

这与 N8 §2 的路径 A 判据完全兼容：只要命中一个 `E8 → 0x10123B20` 且 `ECX=0x10645558`，即可闭合。

## 2 N4-E：`0x10429308` 只有写、没有读

`xrefs(0x10429308)` 返回 2 条：

| 地址 | 指令 | 类型 | 所在函数 |
|---|---|---|---|
| `0x10123DAD` | `MOV [0x10429308],EAX` | 写 | `SV_SpawnServer`（`EAX=0x800`） |
| `0x10125393` | `MOV [0x10429308],EBX` | **写** | `FUN_10125330` |

也就是说：

```
0x10123DA2  MOV EAX,0x800
0x10123DA7  MOV [ESI+0x218],EAX      ; sv.max_edicts
0x10123DAD  MOV [0x10429308],EAX     ; 写 #1
...
0x10125393  MOV [0x10429308],EBX     ; 写 #2（另一个路径）
```

`engine.dll` 内**没有任何指令读取它**。因此 review 担心的「`for (i < global; i++) fixed_array[i]`」
形态在 engine 内不存在——没有读者，就没有固定数组消费者。

保守保留两点：

1. 这是 Ghidra xref 完整性范围内的结论；若有代码以「基址寄存器 + 位移」方式访问
   （`&[0x10429308]` 附近的更大结构），xref 列表不会显示。`0x10429308` 属于带 `_DAT_` 前缀的
   重叠符号区，需要按结构体成员再确认一次；
2. 其他模块（`server.dll`/`client.dll`）无法直接以绝对 VA 访问 `engine.dll` 的 `.data`，
   除非经由导出符号/接口；本轮未发现此类导出。

因此 N4-E 暂按「低风险、只写诊断变量」记录；若后续在 `FUN_10125330` 里发现 `EBX` 的来源是
另一个容量值，再升级复核。

## 3 `FUN_10125330` 需要一次小核对

第二条写来自 `FUN_10125330`（`0x10125393`），它与 `SendClientMessages`（`0x101254B0`）相邻，
属于同一发送子系统。下一轮只需确认 `EBX` 在该函数里的定义（是否也是 `0x800`/容量），
即可决定 `0x10429308` 是否还有第二条容量语义。
