## 1 撤回的结论

`reports/network-n1.md` §4 曾写：

> 写入侧带 `bCheckRange=1`，11 位上限 2047；原版 2048 实体不越界 ⇒ 该字段是最大索引
> ⇒ 4096 槽位需要 `0xFFF`，12 位刚好够。

这条推论不成立，两处都错：

1. **推理错**：原版正常运行只说明「原版实际输入落在原编码约束内」，不能反推字段的
   数学语义。容量型字段完全可以在原版取 `2048` 之外的调整值（例如 `实体数-1`、
   `最高索引`、或按块对齐后的容量），从而在 11 位内合法。
2. **结论错**：因此「12 位足够」不是结论，而是四个候选格式之一。

**当前立场**：PacketEntities 消息头的位宽格式**未定**，`12/12`、`13/12`、`12/13`、
`13/13` 均未排除。

### 2.1 为什么 `+0x58` 不能直接认定

参考实现的序列化顺序是：

```
WriteUBitLong(m_nMaxEntries, MAX_EDICT_BITS);
WriteOneBit(m_bIsDelta);
//  若 delta：DeltaFrom、Baseline
WriteUBitLong(m_nUpdatedEntries, MAX_EDICT_BITS);
```

本次已恢复的 L4D2 写侧顺序为：

```
[edi+0x54] (11 位)  @0x101D7362 / push 0xb @0x101D7366
变宽写入（位宽在 ecx）  @0x101D73C8
[edi+0x58] (11 位)  @0x101D73D1 / push 0xb @0x101D73D5
```

读侧顺序为：

```
[edi+0x54] (11 位, mask 0x7FF)        @0x101D747E → 存 0x101D754D
1 位 → [edi+0x5C]                      @0x101D75A2
（delta 分支）[edi+0x64] = -1           @0x101D76A8
1 位（mask 0x103ECE54）
11 位（mask 0x7FF, shr 0xb）            @0x101D7798
```

两种读法都能自洽：`+0x58` 可能是紧接 `m_bIsDelta` 的 `DeltaFrom`，也可能是跳过
`Baseline` 之后的 `m_nUpdatedEntries`。**必须靠「11 位字段出现次数 + 分支条件」
定名**，不能靠顺序猜测。这也是 N2 的 P0 之一。

## 3 更正：内联位图的布局判断

N1 曾写「两处数组基址相差 `0x100`，是两个相邻的 2048 位内联位图」。这条也不成立。

### 3.1 实际证据（两处反编译已入库）

客户端（`CL_CopyNewEntity` = `0x10076A40`）：

```c
*(u32 *)(*(int *)(this + 0xc) + 4) = *(u32 *)(this + 0x18);          // last index
puVar5 = (u32 *)(*(int *)(this + 0xc) + 0xc + (idx >> 5) * 4);        // 内联位图
*puVar5 |= 1 << (idx & 0x1f);
```

服务端（`SV_WriteEnterPVS` = `0x10119490`）：

```c
iVar9 = *(int *)(*(int *)(esi + 0xc) + 0x10c);                        // 取指针
if (iVar9 != 0) {                                                     // 可空
  puVar1 = (u32 *)(iVar9 + (idx >> 5) * 4);                           // 裸位向量，无 +0xC 头
  *puVar1 |= 1 << (idx & 0x1f);
}
```

### 3.2 结论

| 偏移 | 内容 | 形态 |
|---|---|---|
| `+0x04` | 最后写入的实体索引 | `int` |
| `+0x0C` | `CBitVec<2048>` | **内联**，256 字节，占 `0xC..0x10B` |
| `+0x10C` | `CBitVec<2048> *` | **指针，可空**，指向独立分配的裸位向量 |
| `+0x110` | 后续成员 | — |

`0x10C - 0xC = 0x100 = 256` 是**被内联位图的大小解释掉的**，不是「两张位图相邻」。
第二张位图在堆上，单独分配。

### 3.3 修正后的偏移映射与扩容代价

对原偏移 `o`：

```
F(o) = o                     , o <  0x10C
     = o + 0x100             , o >= 0x10C
```

| 项 | 原 | 4096 位 |
|---|---|---|
| 内联位图 | 256 B（`0xC..0x10B`） | 512 B（`0xC..0x20B`） |
| 指针字段 | `+0x10C` | `+0x20C` |
| 后续成员 | `>= 0x10C` | 整体 `+0x100` |
| 对象大小 | — | `+0x100`（不是 `+0x200`） |
| 堆上位向量分配 | 256 B | **512 B**（分配点常量需同步） |

与「两张内联位图」方案相比，扩容位移少一半，但多出一条**独立分配路径**：
该位向量由谁在何时分配（懒分配？构造时？）、失败/为空时的语义，都必须一起处理。
若该对象跨 DLL 接口传递，`sizeof` 与偏移变化会同时影响 `engine.dll` 之外的模块。

**待证（P0）**：两处 `*(this+0xC)` 是否同一结构体类型；`+0x10C` 位向量的分配点与
分配大小常量；是否存在第三张位图。

## 4 边界重算

`data/network_boundary.csv` 已按「语义分支」重写。要点：

| 语义 | 4096 槽位需要的值 | 12 位 | 13 位 |
|---|---|---|---|
| S1 最高有效索引 | `4095 = 0xFFF` | 够 | 够 |
| S2 快照槽位容量 / 条目数 | `4096 = 0x1000` | **不够** | 够（上限 8191） |
| S3 调整编码（如 `n-1`、块对齐） | 由编码决定 | 未知 | 未知 |

`n = 4096` 是 S1 与 S2 的分水岭：S1 下 12 位恰好，S2 下 12 位差 1。因此
**`12/12` 与 `13/13` 之争只能由消费者语义裁定**，不能由位宽算术裁定。

另：`m_nUpdatedEntries` 若为「单报文更新条目数」，还需要它自己的上界——
单条快照是否允许携带全部 4096 个槽位，是**协议设计约束**，不是位宽约束。
这需要从生产者对「每报文最大更新数」的裁剪逻辑里读出来（P0）。

## 7 生产者 / 消费者数据流（本轮恢复）

### 7.1 服务端生产者：`FUN_10119F50`

`0x10119F50`（1446 字节）是服务端组包函数（`CGameServer::WriteDeltaEntities` 同构体），
入参：`(this, from_frame, to_frame, other_frame, bf_write*)`。逐指令恢复的线格式：

| 序 | 字段 | 取值来源 | 位宽 | 指令证据 |
|---|---|---|---|---|
| 1 | 消息类型 | 常量 `0x1A` = 26 | 6 | `push 0x1a` @`0x1011A08A` |
| 2 | `m_nMaxEntries` | `[[to_frame+0x118]+0x0C]` | **11** | `mov ecx,[ebx+0x118]` @`0x1011A025`；`mov ecx,[eax+0xC]` @`0x1011A096`；`push 0xb` @`0x1011A09B` |
| 3 | `m_bIsDelta` | `from_frame != 0` | 1 | 位设置/位清除两分支 @`0x1011A0B0` 区 |
| 4 | `m_nDeltaFrom` | `[from_frame+0x08]` | **32** | `FUN_10290330(v)` → `FUN_1028fd40(v,0x20)` |
| 5 | `m_bUpdateBaseline` | `[from_frame+0x20C]` | 1 | `FUN_10061340([param_2+0x20C],1,1)` |
| 6 | 回填区（保留 32 位） | 常量 0，稍后回填 | 32 | `FUN_10061340(0,0x20,1)` 前先冻结 `edi` 的 bf_write 视图 @`0x1011A127`；见 §11 |
| 7 | 实体体 | EnterPVS / LeavePVS / delta 三态循环 | 变长 | 跳表 `iStack_14c` ∈ {0,1,2,3}；`FUN_10119490()` = EnterPVS |
| 8 | `m_nUpdatedEntries` | 发射计数（回填入保留区） | **11** | `lea ecx,[ebp-0x17c]` @`0x1011A25C`；见 §11 |
| 9 | `payloadBitLength`（原记 `m_nHeaderCount`） | 实体体比特长度 | 20 | `FUN_10061340(esi,0x14,1)` @`0x1011A272`；见 §11 |

**结论 A（硬）**：整条报文里**恰有两个** 11 位字段（序 2、序 8）。因此
`+0x54` = 序 2 = `m_nMaxEntries`，`+0x58` = 序 8 = `m_nUpdatedEntries`。
`+0x58` 的定名由此闭环：生产者侧它是「本次实际发射的实体条目数」计数器，
不再只是「高置信候选」。`§2.1` 提出的两种读法里，`DeltaFrom` 一支被排除——
`m_nDeltaFrom` 是**32 位**（序 4），不是 11 位。

**结论 B（硬）**：实体索引扩容**不触及** `m_nDeltaFrom`（32 位）与
`m_nHeaderCount`（20 位）；受影响的位偏移只有序 2 与序 8 之后的比特流起点。

### 7.2 `m_nMaxEntries` 的写入源：快照对象 `+0x0C`

`FUN_1011D320(manager, tick, maxEntities)`（439 字节）创建 240 字节对象：

```c
obj[1] = tick;                                   // +0x04
obj[3] = maxEntities;                            // +0x0C  ← 直接赋值，无 -1
obj[2] = FUN_101ae9b0(maxEntities * 0xC);        // +0x08 实体槽数组，12 B/项
// 每项初始化 {0, -1, 0}
```

两个调用点 `0x1004F3AE`、`0x1005158F` 都以 `push 0x800`（=2048）传入。

**矛盾与排除**：若发送帧的快照 `+0x0C` 为 2048，则序 2 以 11 位写入会被截断为 0，
原版必然无法工作；原版工作 ⇒ 发送路径上该值落在 `0..2047`。三种互斥解释：

| 编号 | 解释 | 原版取值 | 4096 槽位取值 | 需要位宽 |
|---|---|---|---|---|
| C1 | 该值 = 本帧实体条目数（计数语义） | 数百，<2048 | 4096 | **13** |
| C2 | `[frame+0x118]` 在发送路径上不是快照（链路判断错） | 未知 | 未知 | 未定 |
| C3 | 该值以 `n-1` / 块对齐等调整编码写入 | ≤2047 | 4095 | 12 |

C1 权重最高：`obj[3] = maxEntities` 是直接赋值（未见 `-1`），且 C1 与外部参考用法
（客户端 `CreateEmptySnapshot(tick, msg->m_nMaxEntries)` 后迭代 `m_nNumEntities`）自洽——
容量恰等于本帧条目数。C3 若成立，则 2048 槽位需以 2047 表示，这在原版恒成立、
在 4096 槽位需以 4095 表示，仍落在 12 位内。

### 7.3 唯一剩余裁定探针（新 P0）

在 `0x1011A096`（`mov ecx,[eax+0xC]`）取 `eax` 所指对象，读 `+0x0C`，对照
「本帧实体数」与 `MAX_EDICTS`：

- `值 == 实体数` → C1 成立，`13/13` 定案；
- `值 == 2047` 或 `MAX_EDICTS-1` → C3 成立，`12/13`；
- `值 == 2048` → C2 成立，回追 `[frame+0x118]` 的写入点。

## 8 位宽裁定：`13/13`（工作假设，随 §7.3 收敛）

`m_nUpdatedEntries` 的上界不是协议常量：全量更新（新客户端首个快照）时发射计数
等于本帧实体数，4096 槽位下可达 4096 ⇒ 同样需要 13 位。不能假设它 ≤2047。

| 格式 | 前提 | 结论 |
|---|---|---|
| `13/13` | C1（计数语义） | **当前工作假设** |
| `12/13` | C3，且 `UpdatedEntries` 仍为计数 | 备选 |
| `13/12` | C1，且单包更新数被硬裁到 ≤2047 | 需要证据支持裁剪点 |
| `12/12` | C3，且更新数也被裁到 ≤2047 | 双重附加假设，优先级最低 |

代价：报文头 +4 bit（2×2），序 2 之后的所有字段与实体体起点整体后移 4 bit，读写两侧必须同步。
`m_nDeltaFrom`（32）本身位宽不变，但它之后的所有偏移随之前移；`payloadBitLength`（20）位宽不变。
**另有一处必须同时改**：32 位回填区需扩为 34 位（§11），否则 13 位写入会覆盖实体体前 2 bit。

## 9 位宽不是充分条件：三个 2048 硬边界

即使两个字段改成 13 位，以下三处仍把实体封在 2047：

| # | 位置 | 形态 | 常量 | 扩容动作 |
|---|---|---|---|---|
| B1 | `FUN_1004E310`（下一置位实体） | `CBitVec` 扫描 | `cmp param_2,0x800` + `do{}while(iVar2 < 0x40)`（64 dword） | `0x800→0x1000`、`0x40→0x80` |
| B2 | `CClientFrame+0x10C` | **内联** 256 字节位图 | `memset(...,0,0x100)` @`FUN_1004EAB0`；`lea esi,[ebx+0x10C]` @`0x1011A061` | 256→512 B，后续字段整体 `+0x100` |
| B3 | `SV_WriteEnterPVS` @`0x10119490` | 可空堆位向量 | `[client+0xC]` → `+0x10C` 指针 | 分配点常量 256→512 |

`FUN_1004EAB0` 同时给出帧布局：`+0x104` 实体数组指针（由 `FUN_1011DB40` 释放）、
`+0x108` = `-1` 哨兵、`+0x10C..+0x20B` = 内联位图、`+0x20C` = 位图后 dword
（重置为 0，并被序 5 当作 1 位标志写出）。

**跨类型偏移不可对齐**：`0x1011A080` 有 `mov [edx+0x10C], esi`（把帧的内联位图地址
写成另一对象的**指针**字段）。同一偏移在帧上是内联数组、在另一类上是可空指针，
扩容必须按类型逐个处理，不能用一张全局偏移映射。

## 11 32 位保留区 = 回填区（机制已证实，`11+20+1 = 32`）

### 11.1 冻结视图 + 事后回填的指令证据

`FUN_10119F50` 在写入 32 位零之前，先把**主缓冲区 `edi` 的 bf_write 头拷进本地**：

```
1011a11f  mov ecx,[edi]        ; m_pData
1011a121  mov edx,[edi+4]      ; m_nDataBytes
1011a124  mov eax,[edi+8]      ; m_nDataBits
1011a127  mov [ebp-0x17c],ecx  ; 冻结视图.data
1011a12d  mov ecx,[edi+0xc]    ; m_iCurBit ← 保留区起点
1011a132  mov [ebp-0x178],edx
1011a13b  mov [ebp-0x174],eax  ; 冻结视图.dataBits
1011a144  push 0x20            ; 保留 32 位
```

实体体写完后，三个字段**全部通过这份冻结视图**（`lea ecx,[ebp-0x17c]`）写回同一段比特：

| 顺序 | 写入 | 位区间（相对保留区起点） | 指令 |
|---|---|---|---|
| 1 | `m_nUpdatedEntries`，11 位 | `[0..10]` | 值 `[ebp-0x138]`；`push 0xb` @`0x1011A259`；`call` @`0x1011A262` |
| 2 | `payloadBitLength`，20 位 | `[11..30]` | `esi = [[frame+0x34]+0xC] - [ebp-0x180]`；`push 0x14` @`0x1011A26F` |
| 3 | 回填标志，1 位 | `[31]` | 内联清位 @`0x1011A4B5` / 置位 @`0x1011A2A7` |

`11 + 20 + 1 = 32`，与保留宽度精确相等。**上一轮把这块写成「常量 0」是错的**：它是一段先占位、
后回填的报文头区域，线格式为 `[Updated 11][Length 20][flag 1][实体体]`，实体体起点 = 保留区 + 32。
回填标志同时把 `frame+0x108`（该帧的增量基准）置为 `to_frame+8`，即「本帧是否为全量 / 有无基准」。

### 11.2 对 `13/13` 补丁方案的影响

- `Updated` 由 11 → 13 后，回填区需要 `13+20+1 = 34` 位。若仍留 32 位：第 1 项写到 13，
  第 2 项写到 33，第 3 项落在 34 —— **覆盖实体体前 2 bit**，且不会触发任何检查（见 11.3）。
- 因此补丁必须多改一处：把保留区从 32 位推进到 34 位，实体体起点随之 +2 bit。
  **不能用 `push 0x22`**——`WriteUBitLong` 的 `numBits` 只能是 0..32（§13.1）；合法做法见 §13.2。
- 三处写入共享同一份冻结视图，宽度由调用点常量驱动，改宽度即自动推进 curbit；风险集中在
  **保留区宽度、body 起点、读端消费顺序**三者的同步，而不是逐字段重排。
- 两个序列化器**不一致**：对象版 `0x101D7340` 是 `type/max/32 位/1 位/Updated/Length`，
  手工版是 `type/max/isDelta/[deltaFrom]/flag/[Updated][Length][flag]`。实际发送走手工版；
  对象版是否为陈旧路径必须单独确认，不能拿它反推线格式。

### 11.3 `bCheckRange` 在本 build 中已失效（重要）

`FUN_10061340`（本地 `bf_write::WriteUBitLong`）实际只有两个栈参数：

```c
void __thiscall FUN_10061340(int *this, uint value, int numBits)   // 第三个实参被忽略
{
  if (this[2] < this[3] + numBits) { this[3] = this[2]; *(byte*)(this+4) = 1; return; }  // 只判缓冲尾
  *(u32*)(...) = (&DAT_106df750)[(curbit & 0x1f) * 0x21 + numBits] & ... | value << ...;
```

- 范围检查只针对 **缓冲区剩余位数**（`m_nDataBits`），不针对 **值的表示范围**；
  调用点压入的第三个实参 `1`（`bCheckRange`）被忽略，release 中亦无 `_DEBUG` 断言。
- 数值超出 `numBits` 时按 `DAT_106df750[(shift)*0x21 + numBits]` 掩码**静默截断**。
- 推论一：2048 用 11 位写会**静默变成 0** ——不崩溃、不置 overflow、不断言。因此 §7.2
  「原版必坏 ⇒ 发送值必 <2048」这条论据**强度下调**：它只说明原版若真写 2048 会静默出错，
  不能排除消费者对 0 有特殊处理、或该路径仅在极端条件触发。C1/C2/C3 仍未定案。
- 推论二：`13/13` 补丁**没有内建自检**——位宽写错不报错，只静默错位。
  验收必须走字节级比对（固定实体集合 → 逐 bit 解析报文头），不能依赖断言或日志。

### 11.4 结论等级（本轮核定）

| 结论 | 等级 |
|---|---|
| 两个 11 位字段已确认（`+0x54` / `+0x58`） | 已证实 |

## 13 N2.4 更正：`numBits ≤ 32`，34 位保留区只能"合法写入 + 推进"

> 本节取代 §11.2 第二条与 §12.1 第 3 项。**`0x1011A144: push 0x20 → push 0x22` 作废**：
> `0x22` 不是合法位宽，任何生成器、补丁脚本、文档都不得再输出它。§12.1 其余各项仍成立。

### 13.1 硬约束：`WriteUBitLong` 的 `numBits ∈ [0,32]`

`FUN_10061340`（本 build 的 `bf_write::WriteUBitLong`）入口只检查**缓冲尾**，
第三个栈实参才是位宽，第四个实参（`bCheckRange`）从未被读取：

```
10061346  mov  ecx,[esi+0xc]        ; m_iCurBit
10061349  mov  eax,[esi+8]          ; m_nDataBits
1006134d  mov  edi,[ebp+0xc]        ; numBits
10061350  lea  edx,[ecx+edi]
10061353  cmp  edx,eax
10061355  jle  0x10061364           ; 放得下 -> 主路径
10061358  mov  [esi+0xc],eax        ; 溢出：curbit = dataBits
1006135b  mov  byte [esi+0x10],1    ; m_bOverflow = 1
10061361  ret  0xc
```

主路径用一条算式把 `(curbit&31, numBits)` 折成**一维索引**，只处理两个 DWORD：

```
10061369  and  ecx,0x1f             ; s = curbit & 31
1006136e  shl  ebx,5                ; s*32
10061371  add  ebx,edi              ; + numBits
10061373  add  ebx,ecx              ; + s        ⇒ 索引 = s*33 + numBits
10061375  mov  ebx,[ebx*4+0x106df750]        ; 掩码
10061394  mov  eax,0x20
10061399  sub  eax,ecx              ; 32 - s
1006139b  cmp  eax,edi              ; 只有 32-s < numBits 才走跨 DWORD 尾段
```

三条硬边界：

1. **列宽 33**（`s*33 + numBits`），即 `numBits ∈ [0,32]`。列 33 不存在。
2. 尾段位数取 `numBits - (32 - s)`，隐含 `numBits ≤ 32`；首 DWORD 的移位量是 `curbit&31`。
3. `n = 34` 时索引变成 `(s+1)*33 + 1`，取到的是**下一行的 1 位掩码**；`s = 31` 时索引
   1057 越过 32 行表尾（32×33 = 1056），读到相邻内存。

`numBits = 34, value = 0` 的实际行为：

| 步骤 | 期望 | 实际 |
|---|---|---|
| 首 DWORD 清位 | 清 `[s .. s+31]` 共 32 位 | 只清 `s+1` 这 1 位（掩码 = 下一行第 1 列） |
| 尾段 | 2 位 | 写 `34-(32-s) = s+2` 位到下一 DWORD 低位 |
| curbit | `+34` | `+34`（只有这一步是对的） |

即 **`0x22` 不崩、不置 overflow、不置断言，只静默写错掩码**；而 `value = 0` 时这些位随后
又被回填整体覆盖，所以看起来"能跑"。这正是必须禁掉它的原因：它的正确性依赖"保留区内容
无人读"这一额外前提，一旦回填顺序再变就会立刻暴露。

> 表的落点：掩码基址 `0x106df750` 落在 `.data` 无文件后备的尾部
> （`.data` RVA `0x423000`，`SizeOfRawData` 仅 `0x1C400`，raw 止于 RVA `0x43F400`），
> 表中内容无法从文件静态引用，运行时应由启动期构造。**本节结论只依赖索引算式，不依赖表内容。**

### 13.2 关键修正：保留区不需要"写 34 位"，只需要"推进 34 位"

§11.1 只说了"冻结视图"，本轮补全为**完整 0x18 字节拷贝**（`ebp-0x17c`）：

| 槽 | 值 | 指令 |
|---|---|---|
| `-0x17c` | `[edi+0x00]` pData | `0x1011A127` |
| `-0x178` | `[edi+0x04]` nDataBytes | `0x1011A132` |
| `-0x174` | `[edi+0x08]` nDataBits | `0x1011A13B` |
| `-0x170` | `[edi+0x0C]` **curBit = F** | `0x1011A146`（在 `push 0x20` 之后、`call` 之前） |
| `-0x16c` | `[edi+0x10]` m_bOverflow | `0x1011A150` |
| `-0x168` | `[edi+0x14]` | `0x1011A156`（**全函数只写不读，死存储**） |

因此**保留区只负责推进 `edi` 的游标**，它的 32 个零位会被三个回填字段全量覆盖：
`Updated [F..F+12]`（13）+ `Length [F+13..F+32]`（20）+ `flag [F+33]`（1）= 34 位，无缝。

两个合法方案，都不使用 `0x22`：

| 方案 | 做法 | 字节预算 | 备注 |
|---|---|---|---|
| **A（cave）** | 站点 `0x1011A144` 换 `jmp rel32`（5 B，其余 24 B 填 `CC`/`90`），cave 内：`WriteUBitLong(0,32)` + `WriteUBitLong(0,2)` + 补齐 `[ebp-0x16c]`/`[ebp-0x168]` 两个存储 | 站点 5 B + cave ≈ 60 B | 需要可执行的 `int3` 空洞；两次写各自合法 |
| **B（原地 6 B，推荐）** | `0x1011A156` 的 `89 85 98 fe ff ff`（`mov [ebp-0x168],eax`）→ `83 47 0c 02 90 90`（`add dword ptr [edi+0xC],2` + 2×NOP） | 6 B，无 cave | 先 +2 再由原 `call` 写 32 位 → 落 `[F+2 .. F+33]`，结束游标 `F+34`；容量检查变成 `dataBits < F+34`，与"保留 34 位"等价 |

两方案的不变量相同：**`[ebp-0x170]` 必须保持 `F`（冻结游标初值不被推进）**，
否则整个回填区会再右移 2 bit。方案 B 里 `F`、`F+1` 两位没有被零写覆盖，但它们由
`Updated` 的 13 位回填覆盖（`F..F+12`），不留下脏位。

方案 B 之所以成立，依赖两条静态事实，均已逐指令确认：
`[ebp-0x168]` 在本函数内只有 `0x1011A156` 一处引用（死存储），且 `add` 发生在
`push 0x20`/`push 0` 之前、`[ebp-0x170]` 赋值之后，不会污染冻结视图。

### 13.3 回填标志的位置是"派生"的，会自动迁移到 bit 33

置位路径 `0x1011A2A7` 与清位路径 `0x1011A4A4` 都不是硬编码 bit 31：

```
1011a2a7  mov  ecx,[ebp-0x170]      ; 冻结视图当前游标
1011a2ad  lea  eax,[ecx+1]
1011a2b0  cmp  eax,[ebp-0x174]      ; curbit+1 <= dataBits ?
1011a2b6  jg   skip
1011a2b8  cmp  byte [ebp-0x16c],0   ; 冻结视图 overflow
1011a2bf  jne  skip
1011a2c1  ...                       ; 用 ecx 算字节/位号并置位
```

`[ebp-0x170]` 只在 `0x1011A146` 写一次（= `F`），之后由 `WriteUBitLong` 的
`add [esi+0xc],numBits` 推进：11 → `F+11`，20 → `F+31`（原版落 bit 31）；
改成 13 后：13 → `F+13`，20 → `F+33`（**自动落 bit 33**）。

结论：**不需要"把 bit 31 改成 bit 33"的补丁**，也没有硬编码位号。边界检查
`curbit+1 ≤ dataBits` 即 `dataBits ≥ F+34`，与保留 34 位是同一条件，无需放宽。
`[ebp-0x16c]` 是**保留动作之前**的 overflow 拷贝，不反映保留区自身溢出——原版行为，
本轮未改变；缓冲不足时由上面的 `dataBits` 检查兜底。

### 13.4 位置模型与静态验收判据

定义（全部以比特计，`H` = 报文头起点）：

| 量 | 含义 | 原版 | `13/13` | 差 |
|---|---|---|---|---|
| `H` | `svc_PacketEntities` 起点（`type` 6 位） | `H` | `H` | 0 |
| `F` | 保留区起点 = 冻结游标初值 `= R` | `F` | `F' = F+2` | +2 |
| `B` | 实体体起点 | `B = F+32` | `B' = F'+34 = B+4` | +4 |
| `E` | 实体体结束 = `payload` 结束 | `E = B+len` | `E' = B'+len'` | 取决于实体数据 |

保留宽度恒等式：`B = F + 32`，`B' = F' + 34`，`F' = F + 2` ⇒ **`B' = B + 4`**。
回填落点：`Updated [F'..F'+12]`、`Length [F'+13..F'+32]`、`flag [F'+33]`。

静态验收判据（不需要运行时）：

1. `F' = F + 2`（`m_nMaxEntries` 宽度 11 → 13 的直接后果）。
2. `B' = F' + 34` 且 `B' = B + 4`。
3. **冻结视图结束游标 = `F' + 34 = B'`；主写端结束游标 = `E'`**。两条游标分属两个
   对象（冻结副本 vs 主写端），必须分别核对，不能合并成一个"当前位偏移"。
4. 回填三段的位区间互不重叠且恰好铺满 `[F'..F'+33]`。
5. 固定实体集合下，`E' - B'` 只随实体数据变化，不随头部宽度变化。

接收端判据：必须做**完整 bit 级解码**（`type` 6 → `maxEntries` 13 → `isDelta` 1 →
`[deltaFrom 32]` → `frameFlag` 1 → `Updated` 13 → `Length` 20 → `flag` 1 → 实体体），
不能"先比对首字段就收工"：13 位字段会新跨 DWORD 边界，`bCheckRange` 又已失效（§11.3），
错位是静默的。

### 13.5 冻结游标 / `[ebp-0x12c]` 数据流闭合（原 §12 工作单 P0 第一项）

- `[ebp-0x170]`（冻结 curbit）：唯一写入 `0x1011A146`（= `F`）；唯一推进者 =
  `WriteUBitLong` 的 `add [esi+0xc],numBits`（`esi` = `lea [ebp-0x17c]`）；
  两处读取 `0x1011A2A7` / `0x1011A4A4`。**该槽是冻结视图自己的 `m_iCurBit`，与主写端无关。**
- `payloadBitLength` 的来源更正：`[ebp-0x12c]` 在 `0x10119FF6` 被赋值为 `edi`
  （全函数唯一写入），故 `0x1011A254` 的 `esi = [ecx+0xC]` 就是 **`edi->m_iCurBit`**，
  即 `payloadBitLength = edi->curBit - B`。上一轮把这里记成 `[[frame+0x34]+0xC]` 是错的。

因此"记录长度"与"发送端实际推进的位数"**同源**（同一个 `bf_write` 实例，中间没有换缓冲区）。
"缓冲区是否同一对象"这个问法可以退役，替换为可判定的问法：
**报文里记录的 `payloadBitLength` 是否等于接收端实际消费的位数**。两者一致的必要条件是
`Length` 覆盖 `[B'..E')` 且接收端按同一位宽序列解码；充分性只能由 13.4 的完整解码验收给出。

（用 `[numBits*4 + 0x103ECE50]` 变量掩码表，天然支持任意 ≤32 位宽与跨 DWORD）。
所以 13 位的跨 DWORD 读取**不需要新代码**，只需上述 5 个常量 × 2 个字段。

`0x103ECE84` 的 `ff 1f 00 00`（`0x1FFF`）是 `.rdata` 里已存在的掩码，读端同表
（`0x103ECE50`，列宽 33）中 `col 6 = 0x3F`、`col 11 = 0x7FF`、`col 13 = 0x1FFF`
均已静态核对——**不需要新增常量，也不需要改节**。

### 13.7 结论等级（本轮核定）

| 结论 | 等级 |
|---|---|
| `WriteUBitLong` 的 `numBits ∈ [0,32]`，`0x22` 非法 | 已证实（指令算式 + 尾段逻辑） |
| 冻结视图是 0x18 字节完整拷贝，自带独立 `m_iCurBit` | 已证实 |
| 回填 11+20+1 恰好铺满保留区，`13/13` 后为 13+20+1 = 34 | 已证实（机制） |
| 回填标志位号 = 冻结游标，自动迁移，无硬编码 bit 31 | 已证实 |
| 保留区推进可由 6 字节原地补丁实现（方案 B） | 已证机制；**未做字节级落地与运行验证** |
| `payloadBitLength` 与发送端游标同源（同一 `bf_write`） | 已证实 |
| 读端慢路径支持 13 位跨 DWORD | 已证实（通用变量掩码） |
| `m_nMaxEntries` 在 4096 槽位下必取 4096 | 待验证（C1） |
| `m_nUpdatedEntries` 单报文可达 4096 | 待验证（C2/C3） |
| `13/13` 整体 | 仍是工作假设，不是已证需求 |

**生成器约束**：`tools/net_patch_plan.py` 内置 `numBits ≤ 32` 断言与
`B' = B + 4` 位置不变量，生成补丁计划时若出现 `0x22` 直接抛错——这是本节的可执行落点。

## 14 N2.5：`m_nMaxEntries` 的载体已定位（C1/C2/C3 的结构性结论）

> 一句话：**`svc_PacketEntities.m_nMaxEntries` 的唯一载体是"快照对象的 `+0x0C`"，
> 该字段在构造时被逐字写入、之后永不改写、也永不钳制。** 上一轮把 `push 0x800` 的
> 两个调用点当成这条线的来源，属于**槽位张冠李戴**——它们写的是 `+0x104`，
> 而裸流读的是 `frame->0x118`。矛盾就此关闭，但"运行时到底是多少"仍需测量（§14.7）。

### 14.1 发送端逐指令复核（`FUN_10119F50`）

上一轮记录里 `[ebp-0x18]` 的来源一直是"`param_2 + 0x118`"，本轮改为逐指令核对，
结论不变，但顺带发现**同时存在两个快照槽**，这正是上一轮混淆的根源：

| 指令 | 语义 |
|---|---|
| `0x10119f63 mov eax,[ebp+8]` → `0x10119f6b mov [ebp-0x160],eax` | `param1` 存档 |
| `0x10119f93 mov ecx,[ebp+0xc]` → `0x10119f9e mov [ebp-0x164],ecx` | `param2` 存档 |
| `0x10119f75 mov edi,[ebp+0x14]` | `param4` = `bf_write`（写者） |
| `0x10119fbf mov eax,[ebp-0x164]`<br>`0x10119fcb mov eax,[eax+0x118]`<br>`0x10119fd1 mov [ebp-0x18],eax` | **`[ebp-0x18] = param2->0x118`** |
| `0x10119fd4 mov eax,[ebp-0x160]`<br>`0x10119fda mov ecx,[eax+0x104]`<br>`0x10119fe5 mov [ebp-0x14],ecx` | **`[ebp-0x14] = param1->0x104`**（另一个槽） |
| `0x1011a093 mov eax,[ebp-0x18]`<br>`0x1011a096 mov ecx,[eax+0xc]`<br>`0x1011a099/9b/9d push 1 / push 0xb / push ecx`<br>`0x1011a0a0 call 0x10061340` | **裸流字段 = `param2->0x118->0x0C`，11 位** |

两个槽的分工在后面的分支里可以直接看出来：

- `barrier [ebp-0x14]` 只用于**存在性判断**：`0x1011a29d cmp dword ptr [ebp-0x14],0` /
  `0x1011a2a1 je 0x1011a4a4`（无快照则跳过 frameFlag 回填）。
- `[ebp-0x18]` 既供裸流 11 位（`0x1011a093`），也供**条目表查询**：
  `0x1011a2f3 mov ecx,[ebp-0x18]` / `push esi` / `push ecx` / `call 0x1011c630`。

`FUN_1011C630` 是本轮的身份证据：它是 `(container, index) -> entry` 的两参函数，
`0x1011c643 mov ecx,[ecx+8]` / `0x1011c646 lea eax,[eax+eax*2]` /
`0x1011c649 mov eax,[ecx+eax*4+8]`，即 **`entry = *(container->+0x08 + index*12 + 8)`**。
`+0x08` 是条目数组、步长 12 字节——与 §14.2 的构造器完全吻合，因此
`param2->0x118` **就是**快照对象，不是 frame 上的别的指针。

### 14.2 `FUN_1011D320` = 快照构造器：`+0x0C` 直接存参数

```
1011d35e  6a 3c            push 0x3c                 ; sizeof = 60
1011d360  b9 80 05 64 10   mov  ecx,0x10640580       ; 分配器
1011d365  e8 ...           call 0x1028a2b0           ; 分配
1011d3bb  8b 4d 08         mov  ecx,[ebp+8]          ; arg1
1011d3be  8b 45 0c         mov  eax,[ebp+0xc]        ; arg2
1011d3c1  89 4e 04         mov  [esi+4],ecx          ; +0x04 = arg1
1011d3c6  89 46 0c         mov  [esi+0xc],eax        ; +0x0C = arg2   <<< 逐字，无 -1、无钳制
1011d3c9  ba 0c 00 00 00   mov  edx,0xc              ; 条目步长 12
1011d3ce  f7 e2            mul  edx                  ; arg2 * 12
1011d3e1  e8 ...           call 0x101ae9b0           ; new[]
1011d3ec  89 46 08         mov  [esi+8],eax          ; +0x08 = 条目数组
1011d3f3  83 c0 08         add  eax,8                ; 初始化循环从 entry+8 开始
```

对象布局（0x3C = 60 字节）：

| 偏移 | 语义 | 写入点 |
|---|---|---|
| `+0x00` | 首字段（构造时 `[eax]=0`） | `0x1011d36e` |
| `+0x04` | `arg1`（tick 类） | `0x1011d3c1` |
| `+0x08` | 条目数组指针（`arg2*12` 字节） | `0x1011d3ec` |
| `+0x0C` | **`m_nMaxEntries` = `arg2`** | `0x1011d3c6` |
| `+0x10/14/18` | 清零 | `0x1011d3d3/3d6/3d9` |
| `+0x1c/20/24/28/2c/30/34/38` | 清零 + `+0x38` 引用计数原子变量 | `0x1011d370`–`0x1011d397` |

关键点：`arg2` **原样**落到 `+0x0C`，既不做 `-1`（不转成"最大索引"），也不按
`highest used + 1` 收缩。

### 14.3 全部构造点（`E8 rel32` 定向扫描 + 逐条解码确认）

| # | 调用点 | `arg2`（→`+0x0C`） | 结果去向 |
|---|---|---|---|
| 1 | `0x1004F3B5` | 字面量 `0x800` | `client->0x104`（`0x1004F3BD`） |
| 2 | `0x10051595` | 字面量 `0x800` | `obj->0x104`（`0x1005159A`） |
| 3 | `0x1011D92B` | **全局 `[0x1064576C]`** | 拷贝路径，随后 `edi=[esi+8]` 遍历条目（`0x1011D93D`） |
| 4 | `0x10184744` | **`[esi+0x54]`** | 快照 → 紧随其后 `push 0x11c` 分配 frame（`0x10184749`） |

只有 4 个调用点，全部经 `push` 传参、`ecx = [0x1042906c]`（快照管理器）。

站点 4 的上下文（这就是第 4 轮怀疑的 `+0x54`）：

```
10184733  8b 4e 54         mov  ecx,[esi+0x54]      ; arg2 来源
10184736  8b 87 bc 00 00 00 mov eax,[edi+0xbc]      ; arg1 来源
1018473c  51               push ecx
1018473d  8b 0d 6c 90 42 10 mov ecx,[0x1042906c]
10184743  50               push eax
10184744  e8 d7 8b f9 ff   call 0x1011d320
10184749  68 1c 01 00 00   push 0x11c              ; 紧接着的 frame 分配
```

**站点 4 证实了第 4 轮的假设：`+0x54` 确实是"快照容量"的载体**，而且它是唯一
把容量送进 `frame->0x118` 这条线的路径。

### 14.4 `+0xC` 是写一次字段：没有任何改写点

扫描方法（避开错位假阳性）：先按"加载 `[reg+disp]` 的 6 字节模式"取全部候选，
再**在候选地址处解码**，要求首条指令确为 `mov reg,[reg2+disp]` 且 `reg == reg2`，
然后检查紧随其后的 3 条指令里是否有 `mov [reg+0xc], ...`（同一寄存器）。

| 调度偏移 | 通过解码校验的加载点 | 后续改写 `+0xC` |
|---|---|---|
| `[reg+0x118]` | 23 | **0** |
| `[reg+0x104]` | 30 | **0** |
| `[reg+0x10C]` | 23 | **0** |

即：`m_nMaxEntries` 的生命周期是"构造时定值 → 只读"。因此
**`+0xC` 的运行时值 = 构造参数的运行时值**，没有"后来被收缩成真实实体数"的隐藏步骤。
上一轮的 C1 假设（"`m_nMaxEntries = f(highest network entity index)`"）**不成立**：
它不随实际使用量收缩。

### 14.5 对象身份闭合：`frame = 0x11C`，`+0x118` 是最后一个成员

站点 4 在构造快照后立刻 `push 0x11c` 分配 frame。`0x11C` 字节的对象上
`+0x118` 正好是**最后一个 dword**，与"`frame->0x118` = 指向快照的指针"一致；
再叠加 §14.1 的条目表证据（数组 `+0x08`、步长 12）与 §14.2 的构造器布局，
三处独立观察互锁，`+0x118` 指向快照对象这一点没有剩余歧义。

旁证：调用者 `0x101861CC mov edi,[edi+0x118]` 与 `0x101861D6 mov ecx,[esi+0x118]`
说明该指针还兼作 frame 链的遍历纽带，用 `cmp edi,ebx / je` 终止——这与
"每帧一个快照"的结构自洽。

### 14.6 矛盾裁定（C2 关闭）

| 上一轮的悬案 | 本轮结论 |
|---|---|
| `[to_frame+0x118]+0x0C` 与两个 `push 0x800` 工厂调用点矛盾 | **不矛盾**：`0x800` 的两个站点写的是 `+0x104` 槽；裸流读的是 `+0x118` 槽。两者不是同一条数据流 |
| `+0x54` 是什么 | 快照构造的 `arg2`，即 `m_nMaxEntries` 的直接来源（站点 4） |
| `m_nMaxEntries` 会不会被改写成真实数量 | **不会**（§14.4，写一次） |

### 14.7 仍然只剩一件事要测：`[esi+0x54]` 的运行时值

逻辑推演已经把问题压缩成一个数：`+0x0C` 写一次、无钳制，而裸流只给它 **11 位**。
若 `[esi+0x54]` 在运行期等于 2048，则 11 位写入只会留下 `2048 & 0x7FF = 0`，
接收端会认为"本帧实体上界为 0"。因此**游戏能正常联机这一事实本身就已经蕴含
`[esi+0x54] ≤ 2047`**——但这只是反证，不是测量。

判据（下一步唯一要拿的数）：

| `[esi+0x54]` 的实测语义 | 推论 |
|---|---|
| 恒为 `2048`（`MAX_EDICTS`） | 与"11 位可容纳"直接冲突，必须先解释 2048 如何过线，再谈 4096 |
| `highest used index + 1`，典型值远小于 2048 | 11 位"够用"是**统计意义**上的，不是结构保证；4096 场景下该值会同步变大 |
| `highest used index`（不 +1） | 与 `4096` 槽位、`max index = 4095` 的换算关系需重算 |

同时要静态定位 `+0x54` 的写者（哪个对象、哪个字段），确认它和 `maxEntities`
全局的关系。补充观察：站点 3 的另一路来源是全局 `[0x1064576C]`，两条路径说明
容量既可来自对象字段也可来自全局，**测量时必须说明取的是哪一路**。

### 14.8 结论等级（在 §13.7 基础上的增量）

| 结论 | 等级 |
|---|---|
| 裸流 `m_nMaxEntries` = `frame->0x118->0x0C` | 已证实（逐指令） |
| `frame->0x118` 是快照对象（数组@`+8`、步长 12、`+0xC` 容量） | 已证实（构造器 + 查询函数 + `0x11C` 尺寸三重互锁） |
| `+0x0C` 构造时逐字写入、无 `-1`、无钳制 | 已证实 |
| `+0x0C` 全二进制内无改写点 | 已证实（23/30/23 个校验加载点，0 改写） |
| 快照构造共 4 个站点，`arg2` 分别为 `0x800/0x800/[0x1064576C]/[esi+0x54]` | 已证实 |

### 14.9 方法论更正：字节模式扫描必须逐地址解码校验

本轮开头用 `89 88 18 01 00 00` 之类裸模式扫 `[reg+0x118]` 存储点，得到
"全 `.text` 只有 1 处，位于 `0x1020FB79`"。**该结果是假的**：`0x1020FB30` 起
按 6 字节步长周期性出现 `00 89 88 XX 00 00 00`，从任意偏移线性解码都会
得到 `add byte ptr [ecx+0xXX88], cl` 这类错位指令，而 `89 88 18 01 00 00`
只是错位窗口里的一段字节。

由此定两条硬规则，后续所有扫描都照此执行：

1. **控制流定向扫描**（`E8 rel32`）必须校验 `rel32` 落点并解码确认目标一致；
2. **模式扫描**必须在命中地址处解码，并要求至少一条指令的**操作数形状**匹配，
   不接受"字节序列相等"作为证据；线性反汇编一旦遇到非法指令就停，
   不能用其覆盖长度当作"全节已扫"。

`FUN_1011D320` 的调用者数量因此从"2"更正为"4"（§14.3），这也是本轮
唯一被推翻的旧数字。

## 15 N2.6：站点 4 是**接收方**——撤回 §14 的"唯一入口"结论

> 提交 `0372ffc` 之后继续追 `[esi+0x54]` 的宿主，结论反转：`FUN_10184744` 所在的
> `FUN_101846C0` 是**消费 `svc_PacketEntities` 的一侧**，不是发送端快照的来源。
> 因此 §14.3 / §14.7 中"站点 4 是 `frame->0x118` 这条线的唯一入口"**撤回**。

### 15.1 `esi` 是 `SVC_PacketEntities` 报文对象（四偏移互证）

`FUN_101846C0(esi = [ebp+8], edi = this)` 对 `esi` 的访问全部落在报文类的既有字段上：

| 指令 | 偏移 | 字段图对应 |
|---|---|---|
| `0x101846e7 cmp byte ptr [esi+0x5c],bl` | `+0x5C` | `m_bIsDelta`（1 位，byte 存放） |
| `0x101846ec mov eax,[esi+0x64]` | `+0x64` | baseline sentinel（初值 `0xFFFFFFFF`） |
| `0x10184733 mov ecx,[esi+0x54]` | `+0x54` | `m_nMaxEntries`（11 位） |
| `0x10184778 cmp byte ptr [esi+0x5d],bl` | `+0x5D` | `m_bUpdateBaseline` |
| `0x10184781/0x101847a3 mov eax,[esi+0x60]` | `+0x60` | 报文内标量字段 |
| `0x1018488f lea eax,[esi+0x6c]` | `+0x6C` | **`m_DataIn`（内嵌 `bf_read`，288 位 = 9 dword）** |

`lea eax,[esi+0x6C]` 是决定性证据：**只有报文对象内嵌 `bf_read`**，随后的实体解析
就用这个读者。`+0x54/0x5C/0x5D/0x64/0x6C` 五个偏移同时吻合，`esi` 的身份没有余地。

该函数**没有 `E8` 直接调用者**（全 `.text` 扫描为空），说明它是虚函数——即
"收到 `svc_PacketEntities` → 建立本地 frame + 快照 → 用 `m_DataIn` 解析实体"的
消息处理入口。

### 15.2 由此得到的真实语义：容量**回环**，不是来源

```
10184733  mov ecx,[esi+0x54]        ; 取自刚解析出的报文字段
10184736  mov eax,[edi+0xbc]        ; 本地 tick
1018473c  push ecx / push eax
10184744  call 0x1011D320           ; 用"报文里的 m_nMaxEntries"当新快照容量
10184749  push 0x11c                ; 再建 0x11C 字节的本帧
```

即接收方把线上字段**原样当作自己快照的容量**，`operator new[](N*12)` 直接按 `N`
分配（`0x1011D3CE` 的 `arg2*12`）。这里**没有任何钳制**：不比较 `0x800`、不取 min、
不校验 `N ≤ MAX_EDICTS`。

推论（对 4096 工程是新增约束）：

- 该 11 位字段是**跨端契约**，不是单端常量：发送端写多少，接收端就按多少分配与遍历。
  两端必须同步加宽，单边改动会造成容量与索引循环上界不一致。
- 12 位化之后接收端最坏分配 `4096*12 = 48 KB`，量级无害；真正要核的是**实体索引
  解码循环是否把这个 `N` 当上界**，以及是否另有硬编码 `0x800` 断言。

### 15.3 撤回与保留

| §14 中的说法 | 现状 |
|---|---|
| "站点 4 是 `frame->0x118` 的唯一入口" | **撤回**：站点 4 属于接收路径 |
| "`+0x54` 是容量载体" | **保留且在接收端再次成立**（同一字段名、同一语义） |
| "4 个构造点：`0x800/0x800/[0x1064576C]/[esi+0x54]`" | **保留**（这是构造点的完整清单），但归因变化：只有站点 3 与站点 1/2 可能是发送端 |
| "`+0xC` 写一次、无改写" | **保留**（与本节无关，不依赖站点归属） |
| "`m_nMaxEntries` 不随实际用量收缩" | **保留** |

### 15.4 生产端来源因此收敛到两处，都还没测

| 候选 | 位置 | 静态可读性 |
|---|---|---|
| 全局 `[0x1064576C]` | 站点 3（`0x1011D92B`，`CopyFrom` 式重建） | **不可读**：RVA `0x64576C` 落在 `.data` 无文件后备的尾部（raw 止于 RVA `0x43F400`），启动期才被写入 |
| `client+0x104` 的快照 | 站点 1/2（`push 0x800`） | 构造参数静态已知 = `0x800`，但**尚未找到把它复制进 `+0x118` 的指令** |

这正是矛盾的最后一块：若要 `frame->0x118` 在发送端成立，必须存在一条
"`+0x104` → `+0x118`"或"站点 3 的返回值 → 帧"的路径，二者都还没定位。
在找到之前，**不能宣称发送端的 `m_nMaxEntries` 等于 2048，也不能宣称它小于 2048**。

### 15.5 新增 P0（C4）：接收端的硬上界

`+0x54` 在接收端无钳制这一点，把原来的"发送端够不够宽"问题扩成了两问：

1. 发送端实际写入值（§15.4）；
2. 接收端实体循环是否以 `N` 为上界、以及是否存在 `cmp N,0x800` 之类的独立硬检查。

第 2 问可以直接静态回答（在 `FUN_101846C0` 之后调用实体解析的位置附近找 `0x800`
立即数比较），不需要运行时。**这是下一轮的第一个动作。**

### 15.6 结论等级

| 结论 | 等级 |
|---|---|
| `FUN_101846C0` 的 `esi` 是 `SVC_PacketEntities` 报文对象 | 已证实（5 个字段偏移 + 内嵌 `bf_read`） |
| 该函数无 `E8` 调用者 ⇒ 虚函数入口 | 已证实（扫描为空，含义为"非直接调用"） |
| 接收端用线上 `m_nMaxEntries` 作快照容量、无钳制 | 已证实（`0x10184733`→`0x1011D3C6`→`0x1011D3CE`） |
| 站点 4 不是发送端来源 | 已证实（依赖上一条） |
| 发送端 `frame->0x118` 的建立路径 | **未定位**（P0） |
| 接收端是否另有 `0x800` 硬检查 | **未检查**（C4，P0） |
