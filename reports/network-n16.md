# N16：`[EDI+8]` 就是 `CFrame*` —— 扫描器确实读 `CFrame+0x0C`

> 修正 N15 的两处错误（索引区间、回调推断），并沿唯一调用者把 `[EDI+8]` 的右值追到了底。
> 结论：`FUN_101196C0` 是发送端 `FUN_10119F50` 的**栈上局部对象**，其 `+8` 被写入 `arg3`（帧指针），
> 因此 `FindNextSetBit` 扫描的位图正是 **`CFrame + 0x0C`**。N4-B 由此得到第一个直接消费者。

## 0 本轮三条硬结论

| 项 | 结果 |
|---|---|
| `FUN_101196C0` 的调用者 | **唯一**：`0x1011A3DA`，`CALL` 前 `LEA EAX,[EBP-0x158]` |
| 该对象 | 发送端 `FUN_10119F50` 的**栈局部结构**（非堆、非全局） |
| `[EDI+8]` 的写入 | `0x1011A032 MOV [EBP-0x150],EBX`，此时 `EBX = arg3 = CFrame*`；空分支写 0 |
| 因此 `bitmap_scan` | `= ([EDI+8]) + 0x0C = CFrame + 0x0C` |
| `CFrame+0x0C` 的角色 | **实体位图**（扫描侧已确认；置位侧待另行定位） |

## 1 N15 的两处订正

### 1.1 覆盖区间的起点算错

写入地址 `A(i) = EDI + 0x3C + 4*(i>>5)`，正确区间是：

| 索引 | 写入偏移 | 被破坏的成员 |
|---|---|---|
| 2016–2047 | `+0x138` | 位图最后一个 dword |
| **2048–2079** | `+0x13C` | **新快照指针** |
| **2080–2111** | `+0x140` | **旧快照指针** |
| 2112–2143 | `+0x144` | 结构尾部/栈上相邻局部 |

N15 把 `2049–2079` 写成覆盖 `+0x140` 是错的：要等 `i = 2080` 才会跨过 `+0x13C`。

精确表述：`i = 2048` 时执行 `OR dword [EDI+0x13C], 1`——若该指针最低位原为 0，指针值被改成
另一个地址；若该位已为 1，写入发生但数值不变。风险条件是「`i >= 2048` 且置位分支可达且目标位为 0」。

### 1.2 「回调/虚表槽」的说法撤回

`FUN_101196C0` 有**唯一直接调用者** `0x1011A3DA`，且镜像中不存在 `0x101196C0` 的绝对指针
（`C0 96 11 10` 全镜像 0 命中）。所以它既不是虚函数也不是回调，只是一个内部函数；
`EAX` 传参是编译器优化选择，不构成身份证据。此后统一称「参与实体 delta 处理的函数」。

## 2 调用点与对象的真实身份

```
0x1011A3D0  8D 85 A8 FE FF FF   LEA EAX,[EBP-0x158]   ; 对象在栈上
0x1011A3D6  8B 8D ?  ?  ?  ?    ...
0x1011A3DA  E8 E1 F2 FF FF      CALL 0x101196C0       ; EDI = EAX = EBP-0x158
```

对象基址 `EBP-0x158`，字段映射：

| 对象偏移 | 栈地址 | 写入点 | 值 |
|---|---|---|---|
| `+0x08` | `EBP-0x150` | `0x1011A032 MOV [EBP-0x150],EBX` | **`arg3` = `CFrame*`**（另一分支写 0） |
| `+0x13C` | `EBP-0x01C` | `0x1011A032` 之后的 `MOV [EBP-0x1C],ECX` | `[frame+0x118]` = 帧快照 |
| `+0x140` | `EBP-0x018` | `0x10119FD1 MOV [EBP-0x18],EAX` | `[param2+0x118]` = 旧快照 |
| `+0x014` | `EBP-0x144` | 循环内 | 当前实体索引 |
| `+0x03C` | `EBP-0x11C` | `0x10119713 OR [EAX],EDX` | 编码器自己的 2048 位位图 |

`EBX` 在 `0x1011A032` 处仍是 `arg3`：`0x10119F67 MOV EBX,[EBP+0x10]`，直到 `0x1011A04C`
才被重新赋值为 `arg1`（N5 已逐指令确认）。所以 `[obj+8] = frame` 是确定的。

## 3 由此得到的位图归属

```
bitmap_scan = ([obj+8]) + 0x0C = CFrame + 0x0C
```

这是 `CFrame+0x0C` 的第一个**消费者**证据：

- 2048 位内联区域不再是「尺寸配平的巧合」，而是 `FindNextSetBit` 真正扫描的对象；
- 因此 `CFrame` 的 `0x11C → 0x21C` 不再是纯假设——**但要先扩容 `CFrame`，才敢扩容扫描器上界**：
  当前扫描至多 `0x800` 位，读不到 `+0x10C` 之后；一旦放到 4096 位而上界仍是 `0x11C` 的旧对象，
  会读到对象之外；
- 置位侧尚未定位：`FUN_101196C0` 里 `OR` 写的是**它自己的** `+0x3C`（栈上），不是 `frame+0x0C`。
  谁往 `frame+0x0C` 置位仍需下一轮确认（候选：发送端其它 `FindNextSetBit` 调用点附近）。

## 4 两个位图并存（重要）

| 位图 | 位置 | 谁写 | 谁读 |
|---|---|---|---|
| 编码器位图 | `stack_obj+0x3C`（`EBP-0x11C`） | `FUN_101196C0` 的 `OR` | 未观察到 |
| 帧位图 | `CFrame+0x0C` | 待定位 | `FindNextSetBit`（本轮已证） |

两者**不是同一块内存**。因此：

1. N4-F 的「delta 编码器对象扩容」是**栈局部结构扩容**（`sizeof ≈ 0x144`，落在发送端 `0x180` 栈帧内），
   扩容 `0x100→0x200` 需要把栈帧从 `0x180` 扩到 `0x280` 并平移所有相关局部——比堆对象迁移更麻烦；
2. 编码器位图的溢出（`i>=2048`）会改写 `obj+0x13C`/`+0x140`，即**栈上的两个快照指针**；
3. `CFrame` 的迁移是**独立**的一条线，且现在有了消费者证据。

## 5 旧快照数组边界（未闭合，需单独建账）

`0x101196E9` 先读旧数组、`0x101196F0` 后才比较新快照计数。是否可达取决于：

- `EAX+EBX` 的索引是否恒等于当前实体号（`LEA EAX,[ECX+ECX*2]; ADD EAX,EAX; ADD EAX,EAX` ⇒ `i*0xC`，是）；
- 抵达前是否已有旧快照容量保护（目前未见）；
- 新旧快照是否可能不同容量——N3 记录 `FUN_1011D320` 两处调用点传字面量 `0x800`，
  说明**某些快照可能不随 `sv.num_edicts` 扩容**，这条风险独立于位图。
